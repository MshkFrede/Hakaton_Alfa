# Исследование, границы MVP и ключевые решения

## Кто пользователь и что ему нужно (JTBD)

Пользователь — собственник, директор или бухгалтер малого бизнеса. Банковской экспертизы у него обычно нет, времени мало.

| Когда… | хочу… | чтобы… | Как решено в продукте |
|---|---|---|---|
| нужны деньги под конкретную задачу | понять, какой кредит мне подходит, без банковских терминов | не ошибиться с продуктом и не тратить время на консультации | Выбор начинается с **задачи бизнеса**, продукт подбирается и объясняется |
| заполняю заявку | не вводить то, что банк и так может узнать | не тратить время и не ошибаться в реквизитах | Реквизиты, руководитель, ОКВЭД — **из ЕГРЮЛ по ИНН** |
| выбираю сумму и срок | заранее понять, потяну ли платёж и одобрят ли | не получить отказ из-за завышенной суммы | **Живой калькулятор нагрузки** и оценка «комфортной суммы» до подачи |
| заявка подана | видеть, что с ней происходит, и знать, нужно ли что-то от меня | не звонить в банк и не ждать вслепую | **Трекер этапов**, статус простыми словами, блок «что нужно от вас» |
| банк не готов одобрить как есть | получить альтернативу, а не просто отказ | всё-таки решить задачу | **Контрпредложение** с понятными новыми условиями, принять в один клик |
| банку не хватает информации | быстро досдать документы | не начинать всё заново | **Дозапрос документов** и загрузка прямо в кабинете, заявка сама возвращается в работу |
| пришёл отказ | понять причину | знать, что исправить | Причины в **человеческих формулировках** без раскрытия модели |

Для банка (кредитный специалист):

| Когда… | хочу… | Как решено |
|---|---|---|
| заявка простая | чтобы её не было в моей очереди | **Автоматическое решение** для рейтингов A/B в лимитах продукта |
| разбираю заявку | видеть всё в одном месте и понимать, почему система рекомендует так | **Досье**: данные трёх источников, разбивка балла, обоснование политики, причины ручного разбора |
| принимаю решение | иметь варианты, а не только «да/нет» | Одобрить / изменить условия (с пересчётом платежа) / запросить документы / отказать |
| нужно объяснить решение аудиту | иметь журнал | **Журнал событий** с внутренними комментариями, снимки данных источников, версия модели |

## Границы MVP (MoSCoW)

**Must — сделано:**
- Сквозной путь: потребность → продукт → заявка → проверка полноты → обогащение → скоринг → решение → подписание → выдача.
- Четыре исхода решения и петли «контрпредложение» и «дозапрос документов» внутри продукта.
- Две роли и два интерфейса над одной заявкой, ролевой доступ.
- Машина состояний с проверкой переходов, журнал событий.
- Моки ЕГРЮЛ/ЕГРИП, БКИ, ФНС.
- Docker Compose, синтетические данные, демо-учётки, документация.

**Should — сделано:**
- Подбор продукта по задаче (JTBD), автозаполнение по ИНН, калькулятор нагрузки до подачи.
- Объяснимый скоринг для специалиста и человеческие формулировки для клиента.
- Гибридное решение: авто для простых случаев, специалист для пограничных.
- Отказоустойчивость интеграций: таймауты, ретраи, деградация в ручной разбор.
- Очередь задач с outbox, оптимистичная блокировка, идемпотентность.
- Метрики конвейера: доля авторешений, время до решения.

**Could — не сделано (следующие шаги):**
- LLM с открытыми весами: краткое резюме досье для специалиста, распознавание выписок. Основной сценарий от этого не зависит, поэтому отложено.
- Уведомления в кабинете (центр уведомлений), push через WebSocket/SSE.
- Несколько пользователей одной компании с разными правами (директор / бухгалтер).
- Повторное использование данных: «подать заявку как прошлую».

**Won't — сознательно вне рамок:**
- Реальные интеграции и реальная ЭЦП (нет доступа к системам банка — условие кейса).
- Залоговый модуль, график платежей, обслуживание кредита после выдачи.
- Мобильное приложение (запрещено условиями).

## Ключевые решения и обоснование

| Решение | Альтернатива | Почему так |
|---|---|---|
| **Go-монолит с чёткими модулями** | Микросервисы | Один сервис проще запустить и проверить. Границы модулей (`scoring`, `policy`, `integrations`) проведены так, что выделение в сервисы механическое |
| **Очередь задач в PostgreSQL (outbox + SKIP LOCKED)** | Kafka / RabbitMQ | Транзакционная гарантия «статус + задача» без распределённых транзакций, одна зависимость. Kafka — путь масштабирования |
| **Скоринг ≠ решение** — два пакета | Одна функция «одобрить/отказать» | Прямое требование кейса. Позволяет менять модель риска и политику банка независимо, делает решение объяснимым |
| **Балльная карта, а не ML** | Градиентный бустинг на синтетике | На синтетических данных ML ничего не доказывает. Скоринговая карта прозрачна, объяснима и проверяема, её веса легко защищать |
| **Фронтенд без сборки и npm** | React + Vite | Ноль сторонних JS-пакетов: нет рисков цепочки поставок, нет node-тулчейна в сборке, проще аудит и воспроизводимость. Для форм, таблиц и статусов фреймворк не нужен |
| **Опрос статуса раз в 2 с** | WebSocket / SSE | Надёжно через любые прокси, тривиально в отладке, нагрузка мизерная. SSE — следующий шаг |
| **Отказ источника → ручной разбор, а не ошибка** | Остановить заявку | В реальности источники падают. Клиент не должен получать отказ из-за сбоя у бюро |
| **Код подписи показывается в интерфейсе** | SMS | Условие кейса: весь сценарий внутри продукта. Механика подписи (код, проверка, фиксация времени) сохранена |
| **Деньги в целых рублях (`bigint`)** | `float` / копейки | Без ошибок округления. Для кредитов МСБ копейки в сумме не нужны |

## Упрощения (явно)

1. **Внешние источники — моки** с упрощёнными контрактами и синтетическими данными. Смысл интеграции (что запрашиваем и как используем) сохранён.
2. **Подписание — симуляция ПЭП:** 6-значный код показывается в интерфейсе вместо SMS. Документ договора не формируется.
3. **Выдача — симуляция:** генерируется номер счёта, факт зачисления фиксируется событием.
4. **Аутентификация** — собственный JWT вместо корпоративного IdP. Один пользователь привязан к одной компании, полномочия подписанта не проверяются.
5. **Каталог продуктов и параметры политики** — в коде, а не в настраиваемом справочнике.
6. **Веса скоринга и PD** — иллюстративные, не откалиброваны на реальных данных.
7. **Документы** хранятся в БД без антивирусной проверки. Содержимое документов автоматически не анализируется — их смотрит специалист.
8. **Пауза между шагами** обработки (`PROCESSING_STEP_DELAY=2s`) добавлена специально, чтобы в демо было видно движение заявки по статусам. В бою она равна нулю.
